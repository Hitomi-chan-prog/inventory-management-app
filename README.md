# ストックノート — 在庫管理・発注アラートWebアプリ

HTML・CSS・JavaScriptで開発する、フレームワークを使わない学習・ポートフォリオ用アプリです。

## 現在の範囲：STEP 2-4（商品編集・一覧連携・複数タブ対応）

通常モードはIndexedDBから商品と在庫を読み込みます。初回は商品0件です。画面右上の「デモモードへ」で切り替えると、仮データで在庫一覧、商品登録／編集、商品詳細、入出庫・取消履歴を表示します。一覧・詳細から入庫／出庫ダイアログ、履歴から取消ダイアログを開けます。検索・要発注絞り込み・履歴の商品／種別絞り込みも試せます。

**通常モードの商品登録・編集を実保存できます。実際の在庫更新・取消・CSV出力・商品削除は未実装です。** IndexedDBのDB・ストア作成と読み取りは実装済みです。 デモモードの確認ボタンはメッセージを表示するだけです。予定在庫は参考表示で、在庫不足などの業務判定はまだありません。再読み込みすると通常モードに戻ります。モード切り替え時は一覧へ戻り、フォームの入力破棄を確認します。通常モードでは入庫・出庫・取消は利用できません。

## 起動方法

リポジトリのディレクトリで次を実行します（Python 3が必要）。アプリを表示するだけならビルドやnpmインストールは不要です。Node.jsとPlaywrightは自動テスト専用です。

```sh
python3 -m http.server 8000 --bind 127.0.0.1
```

ブラウザでローカルサーバーのポート8000を開いて確認してください。停止はターミナルでCtrl+C。VS CodeのローカルHTTPサーバー拡張からも起動できます。アプリ本体に依存する外部ライブラリ・外部フォント・APIはありません。

## JavaScriptの読み方

1. `demoProducts`・`demoMovements`・`demoCancellations`は表示専用の仮データです。`updateMode()`がデモモードのときだけ表示用配列へ渡します。商品ID、元取引IDで関連付けています。DBの実装ではなく、履歴も全件分の台帳ではありません。
2. `renderRoute()`はURLの`#inventory`や`#product/p1`を読み、対応する表示関数を呼びます。`hashchange`はURLのこの部分が変わった時のイベントです。ブラウザの戻る・進むでも切り替わります。
3. `screen.innerHTML`で画面の中身を差し替えます。フォームを離れると未保存入力は消えます。将来、入力離脱の確認を検討します。
4. `filter()`は条件に合うデータを選び、`map()`はデータを表示用HTMLに変換します。検索条件は在庫一覧の再描画に使い、ダイアログを閉じても残ります。
5. クリックは親の`screen`で受け取り、`data-operation`から入庫・出庫・取消を判断します。動的に作ったボタンにも対応する「イベント委譲」です。
6. `showModal()`でダイアログを開き、`close()`で閉じます。Escapeでも閉じ、元のボタンへフォーカスを戻します。
7. `preventDefault()`はフォーム送信によるページ移動を止めます。通常モードでは入力検証後に商品登録・編集をIndexedDBへ保存します。デモモードは仮データ専用で、確認メッセージだけを表示し保存しません。
8. 商品フォームは`novalidate`でブラウザ標準の吹き出しを止め、`validateProductInput()`で日本語の項目別エラーを表示します。前後空白を除き、商品コードは大文字に統一します。発注点は前後空白除去後に半角の十進数字だけを許可し、形式確認後に数値へ変換して安全な整数か検証します。小数・負数・指数・16進表記は拒否します。入力すると前回のメッセージを消します。
9. `escapeHtml()`はHTML本文や属性に挿入する文字の`<`や引用符を無害な表記へ変換します。入力の`value`やメッセージの`textContent`へ直接設定するときは変換不要です。
10. エラーは`aria-describedby`で入力欄と関連付け、`aria-invalid`で不正な項目を示します。最初のエラーへフォーカスします。

## 保存について

通常モードの商品登録で商品と初期在庫0をIndexedDBへ保存します。デモデータは保存しません。通常モードの編集は保存します。バックアップ・復元も未実装です。IndexedDBのデータは同じオリジン・ブラウザプロファイル内に限定され、ブラウザデータ削除などで失われる可能性があります。

STEP 2-1レビュー修正：検索は元の文字列で行い、HTML出力時だけエスケープします。商品コードはASCII形式の検証後に大文字化します。数値フィールドもHTML出力時にエスケープします。再発防止を含むテスト集計は`docs/test-plan.md`を参照してください。

## STEP 2-2のDB設計

`js/inventory-db.js`は画面を直接操作せず、DB接続・読み取り・検証を担当します。

- DB名：`stock-note`、バージョン：1。
- `products`：主キー`id`。`productCode`にuniqueインデックス。
- `stocks`：主キー`productId`。
- `InventoryDB.open()`：接続を再利用。失敗・8秒のタイムアウト・更新待ちを日本語に変換します。
- `InventoryDB.close()`：接続を閉じます。モード切り替え・ページを離れた際にも実行します。
- `InventoryDB.readProducts()`：両ストアを同じ読み取り専用トランザクションで読み、完了後に検証して画面用データへ変換します。
- IDはUUID形式、商品コードは正規化済み、日時はUTCのISO文字列、数量・発注点は0以上の安全な整数、更新番号は1以上とします。文字数・空白・商品と在庫の1対1対応も検証します。
- 不正データは勝手に削除・補正せず、一覧を止めてエラーを表示します。論理削除済みの商品も検証し、通常一覧からだけ除外します。
- `onversionchange`で接続を閉じ、他タブのDB更新を妨げません。新しいDBバージョンを旧アプリが開く場合や不正スキーマもエラーにします。
- 商品登録の重複は一意インデックスと同じreadwriteトランザクションによって防止します。商品編集はversion照合と更新を同一トランザクションで実行し、競合を検出します。

### 3つのIndexedDB API

`indexedDB.open()`はDBを開く入口です。初回やバージョン変更時は`onupgradeneeded`が発生し、そこで構造を準備します。`createObjectStore()`は商品や在庫を入れる保存領域を作ります。`transaction()`は複数の読み書きを一組として扱う仕組みで、読み込みでは`readonly`、商品登録では`readwrite`を使用します。

### 画面の状態

読み込み中・正常な0件・読み込み失敗は別表示です。失敗時の「再読み込み」で再試行できます。`loadGeneration`は読み込みの世代番号で、モード変更や再試行前の古い結果を無視します。登録フォームへ移動して入力中なら、読み込み完了で入力を消しません。

デモモードは固定配列だけを参照します。DBへの仮データ投入はありません。自動テストだけが、隔離したブラウザ内で検証用のデータを投入します。

### 削除状態・日時の整合性とエラー通知

- 論理削除済み（`deletedAt`あり）の商品は、関連する在庫が0でなければ読み込みエラーにします。不正データは自動削除・自動修正しません。
- 在庫更新日時は商品作成日時以降、商品削除日時は商品最終更新日時以前であることを検証します。
- 将来の商品削除処理では`deletedAt`の設定と同時に`updatedAt`も更新します。商品と在庫の更新日時を常に一致させる必要はありません。
- `#db-notice`は商品フォームの外側のDB専用通知です。読み込み失敗や接続終了を`textContent`で表示し、入力の再描画は行いません。商品入力時の成功メッセージとは独立しているので、入力を続けてもDBエラーは消えません。再読み込み開始・モード切り替え時に解除します。

## STEP 2-3：商品登録の処理

`InventoryDB.registerProduct(input, { mode:'normal' })`が保存の入口です。画面とは別に共通入力検証を実行し、正規化した商品コード、UUID、UTC日時、version 1を設定します。デモやモード未指定の呼び出しは拒否します。

1. `readwrite`トランザクションで両ストアを開き、既存データの整合性を再確認します。同じトランザクション内なので、確認と追加の間に別タブの書き込みが割り込むことを防ぎます。
2. `products.add()`と`stocks.add()`で商品・初期在庫0を追加します。上書き用の`put()`は使いません。削除済み商品も残っているため、商品コードのunique制約が再利用を防ぎます。
3. 個々の追加成功では成功を返しません。`complete`は全処理が確定した通知で、この時点だけPromiseを成功にします。
4. `abort`は全処理の取り消しです。途中の例外・重複・強制中止で、商品だけ／在庫だけが残らないようにします。日本語で失敗を返し、入力は保持します。
5. 画面は保存中の二重送信・リンク操作・モード切り替えを抑止します。DB読み込みが未完了・エラーなら登録しません。保存後は一覧を取得し直して集計を更新します。
6. 保存完了後に一覧取得だけが失敗した場合は、登録失敗とは区別し「登録済み・再登録不要」と案内します。再試行で二重登録を促さないためです。

通常モードの登録画面URLを直接開いた場合も、バックグラウンドでDBを読み込みます。通常モードの編集は保存し、登録・編集の確定後に別タブへ変更を通知します。

### 登録後に一覧取得が失敗した場合

登録済みという事実と、一覧取得の失敗は分けて案内します。一覧・詳細などを表示中なら古い商品表や集計をエラー画面へ切り替え、「再登録せず一覧を再読み込み」と表示します。登録フォームが表示中なら再描画せず入力を保持し、登録済みボタンを無効のままにします。表示の変更だけを行い、保存済みの商品・在庫は変更しません。

モード切り替えの自動テストは、クリック直後の行数を確認せず、期待するモード名・DBの読み込み完了・一覧行数がそろうまで待ちます。固定時間のsleepは使用しません。

## STEP 2-4：編集と複数タブ

- `readProducts()`は画面用データにも`version`を返します。編集フォームは開いた時点の番号を`expectedVersion`として保持します。
- `updateProduct(id, expectedVersion, input, {mode:'normal'})`は共通検証後、最新データをreadwriteトランザクションで読みます。商品コードの変更と削除済み商品の更新を拒否します。
- 同じトランザクション内で最新versionを比較し、一致した場合だけ商品名・単位・発注点・updatedAt・versionを更新します。在庫レコードは変更しません。
- 例：2タブがversion 1を開き、Aが保存するとversion 2になります。Bの「version 1を編集した」という保存要求は拒否されます。入力を控え、一覧から最新情報を開き直して内容を比較してください。自動上書き・自動再送はしません。
- 通常モードの商品単位は実履歴がまだないため編集できます。将来履歴保存を導入する際は、実履歴がある商品の単位変更を拒否する必要があります。
- DBのcomplete後に`BroadcastChannel`で「商品が変わった」ことだけを通知します。受信側はDBから取得し直し、通知に含まれるデータを直接画面に使いません。
- 入力中は通知を案内するだけで、フォームや保持中versionは変更しません。保存時のDB照合が最終防御です。デモモードは通知を無視します。
- 保存中の通知は後続の再取得へ回します。通常の再取得も世代番号で古い結果を破棄します。通知機能が未対応・利用不可でもversion照合は有効ですが、他タブの表示更新は画面再読み込みが必要です。
- 編集成功後の再取得失敗は「編集済み・再保存不要」と表示し、古い集計を正常表示しません。編集中フォームなら入力を保持します。

編集・登録の実保存もアプリ本体はHTML・CSS・JavaScriptとブラウザAPIだけで動きます。Node.jsとPlaywrightはテスト専用です。

## STEP 2-4レビュー修正：保存結果と検索条件

`saveResult`は直前に確定した保存操作の結果、`dbState`は一覧取得の状態です。保存APIがcomplete後に成功を返したら、フォーム外の`#save-notice`へ保存完了を表示します。その後の読み込み成功・失敗、画面移動、他タブ通知では保存結果を消しません。後続の読み込みが失敗しても「編集は完了しています。再保存は不要です」と案内し、古い表・集計は表示しません。フォームは再描画せず入力を保持します。

保存結果は次の条件で解除します：入力検証とDB準備確認に合格した新しい通常モードの保存操作を開始する時、モードを切り替える時、ページを再読み込みする時。入力変更や一覧再取得だけでは消しません。この通知は現在の未保存入力ではなく、直前の確定済み操作を示します。通知のためにDBを再保存する処理はありません。

`inventoryFilters`が検索文字列と「要発注のみ」を画面のDOMとは別に保持します。通知・一覧再取得・同じモード内の画面移動後にも復元し、最新データへ再適用します。検索文字はHTMLへ挿入せず入力欄のvalueに設定します。モード切り替え・ページ再読み込みでは両条件を初期化します。通常の商品とデモ商品は引き続き別々に表示します。

## DBエラーの分類

保存APIは日本語メッセージと`code`を持つエラーを返します。`INPUT`（入力不正）、`MODE`（デモでの保存要求）、`DUPLICATE`（重複）、`CONFLICT`（version競合）、`NOT_FOUND`（対象なし）は業務上の拒否として扱い、DB全体を異常と判断しません。

`DATA`（データ不整合）、`CONNECTION`（接続失敗・タイムアウト）、`SCHEMA`（構造不正）、`STORAGE`（読み書き中の例外・abort）はDBの信頼性に関わるエラーです。未知のエラーも安全側で同じ扱いにします。保存失敗時にはフォームを再描画せず入力を保持し、商品キャッシュを無効化して、一覧・詳細で古い情報を正常表示しません。元のDBは修復・削除しません。保存完了済みの結果は従来どおり別状態で保持します。

## bfcacheからの復帰

戻る・進むでブラウザがページをメモリから復元した場合（`pageshow.persisted === true`）、登録・編集フォームのDOMは再作成しません。DBだけを背景で読み直し、入力と編集開始時のversionを保持します。他タブの更新があれば、保存時に元のversionとの比較で競合を拒否します。読み込みエラーは独立通知へ表示し、一覧・詳細へ移動しても古いキャッシュを正常表示しません。デモモードでは復帰時のDB再取得を行いません。

bfcacheを使うかはブラウザが判断します。キャッシュ破棄や通常の再読み込み時の入力復元は対象外です。特にキャッシュ中のページへのBroadcastChannel配信はbfcacheを破棄する場合があります。
